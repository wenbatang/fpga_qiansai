# 四风格 720p 的帧率优化与证据

本页对应独立工程 `camera_art_30`。原 `style_model/elinx` 和已认可的 RF33 工程保持原样。本工程选择参考项目的梵高、剪纸、漫画、水墨四组 C8 学习参数，本地槽为 0、1、2、3；这些参数与旧 RF33 六通道模型不是同一个网络。

**当前生产 RTL 的四种风格均完成了完整 1280×720 CNN/DMA 数值仿真，最慢为 35.478367fps，全部 921600 个输出像素与独立整数参考完全一致。这是指定有界 AXI 服务模型下的处理吞吐；尚不能称作实板摄像头、DDR、HDMI 并发稳定 30fps。** 最终可下载文件、资源和时序须同时检查本工程同次构建的 [signoff.json](../build/720p/signoff.json) 和使用说明，不能由本页的数字仿真成绩替代。

## 1. 47 风格工程做得好的地方

参考实现的优势集中在算术结构和保留内容的方法，风格数量本身不会将每一帧的运算做 47 次。

1. 输入和输出都是 1280×720。先对图像做 2×2 整数均值池化，CNN 在 640×360 特征上运行；最终将预测的 RGB 残差最近邻恢复，再与完整原图相加并饱和。因此网络计算量明显下降，原图中的轮廓和高频细节还能沿旁路保留。内部半尺寸特征不是将外部输入或 HDMI 偷换成 640×360。
2. 核心采用 stem 3×3、四组 depthwise 3×3 + pointwise 1×1 和残差、最后的有符号 RGB head。空间卷积与跨通道混合分开，避免每个空间采样都做完整 C×C 矩阵乘法。
3. 四个 depthwise 层和 head 的学习参数在参考项目的 47 个模式间共享。共同常量编译进硬件；风格相关的 stem 和 pointwise 参数通过 CPU 装载。47 个模式只需保留不同权重，不需要 47 套硬件引擎。
4. 定点定义明确：像素/隐藏激活 u8、权重 i8、偏置和累加 i24、舍入 i25、逐输出通道二的幂移位，负数也按 round-half-up，隐藏层饱和到 0–255，head 残差限制到 −510…510。四组真实参数已与独立 int64 参考比对。

每个半尺寸特征像素的 MAC 数为：

| 组成 | MAC |
| --- | ---: |
| stem：3×8×3×3 | 216 |
| 四个 DW：4×8×3×3 | 288 |
| 四个 PW：4×8×8 | 256 |
| head：8×3 | 24 |
| 合计 | 784 |

不计 halo 时，一帧为 230400×784=180633600 MAC，折算每个原图像素 196 MAC；旧 RF33 六通道 dense 模型为每原图像素 1296 MAC。当前十条带的中心宽 128、左右 halo 各 32，总宽 192，处理 345600 个半尺寸特征像素，实际为 270950400 MAC/帧。这个减少来自网络结构变化，不能说成单纯调整 PLL 获得了同画质加速；画质对照见 [model_quality.md](model_quality.md)。

## 2. 本轮三个阶段的同类完整帧成绩

各项均为 100MHz UI、约 166.6MHz 独立 CNN 时钟，真实厂商异步 FIFO，16 拍读突发、单拍 AXI128 写，包含最终 B 响应屏障。有界服务模型相同；未包括真实摄像头、DDR 物理控制器和 HDMI 并发流量。

| 阶段 | 完整720p UI周期 | CNN/DMA模型fps | 主要变化 |
| --- | ---: | ---: | --- |
| 原47风格参考，梵高 | 4065356 | 24.598092 | 单像素 PW 上下文，每像素等待流水排空 |
| 新四风格，PW双上下文，梵高 | 3713814 | 26.926497 | PW连续发射，输出打包仍等待当前字的B |
| 当前生产，梵高 | 2818615 | 35.478418 | PW双上下文 + 两个128bit输出环形槽 |

第二阶段的生产 DMA 源码保存在本地 [baseline_pw_only](../build/baseline_pw_only/README.md)。独立实验候选和它的收据保留用于追溯；**最后一行已经重新针对生产源路径执行，并不是把实验候选的收据改名冒充生产结果。**

| 0 | 梵高 | 921600 | 2818615 | 35.478418 | 0 |

生产验证入口为 [sim/full/verification.json](../sim/full/verification.json)。它包含四个 `per_style` 条目、全部源/模型/输入/期望/配置指纹、真实日志指纹、第三输出槽信息和聚合最低 fps。周期的几个时钟差异来自异步时钟相位和有界握手位置，不是风格之间的计算复杂度改变。仿真的 CNN 周期为 6.002ns，用于覆盖非完全重合的 UI/CNN 时钟相位；UI 周期为 10ns，fps 直接按真实运行的 UI 周期计数计算。

## 3. PW 如何去掉空转

原点卷积只有一份输入、skip、结果存储。8 个输出通道各发射一拍后，还要等待六级算术流水完成，再等待完整输出被接收，才允许下一像素进入。隐藏层连续像素的接收/输出间隔约 16 个时钟。

新 [tiny_pointwise.sv](../rtl/tiny_pointwise.sv) 保留同样的八个乘法器和算术位宽，增加两套像素上下文：输入、skip、inside、输出结果各自锁存。每条流水令牌携带 context 和 channel；context 只有在其完整输出被下游接收后才能重用。两个上下文交替发射，使下一像素的点乘与上一像素的舍入/写回重叠。

- 四个隐藏 PW 的稳态输出间隔实际验证为 **8clk**，512 个像素总计 4105clk。
- head 不成为新的瓶颈：512 个像素 2820clk，最大输出间隔 8clk。
- 下游长时间不接收时，两份 context 可分别保存未消费结果；已提交输出保持稳定，未消费结果不会被新输入覆盖。
- reset 清空 occupied/issued/finished 和流水令牌。权重配置接口与共享 head 常量接口保持不变。

[sim/pointwise/verification.json](../sim/pointwise/verification.json) 覆盖四组真实学习参数 × 四个隐藏 PW/head × 连续输入、气泡和长背压、在途复位，共 30720 个输出像素。它只证明此模块的数值和握手，不是整机帧率证据。

## 4. 输出打包如何与 DDR 等待重叠

只有一个 `output_word` 时，收齐八个 RGB565 像素后必须停止打包，依次等待 AW/W 接收、B 返回，才能收下一组八像素。PW 算得更快后，这个等待成为明显瓶颈，完整帧仍只有 26.93fps。

当前 [video_tile_engine_async.sv](../rtl/p720/video_tile_engine_async.sv) 用两个 128bit 环形槽替代单个打包字。正在 AW/W/B 事务中的字也占一个槽；另一个槽可继续接收下一组像素，**没有把 CNN 的在途 B 数扩大到两个**。

1. producer 向空闲槽逐个写 RGB565，第一像素锁定该字地址，第八像素才将完整字入队。
2. consumer 将队首地址和数据暴露给 AXI，AW 和 W 允许独立接受。队首在背压期间保持稳定。
3. 只有真实 B 握手后，队首槽才归还。两个槽满则停止接收需保留的 CNN 输出，halo 输出仍按规则丢弃。
4. 错误使整帧失败；已经暴露的活动事务继续排空，未发的排队字不再发出。下一作业从清空状态重新开始。
5. 全部条带、全部保留像素、空输出队列、最后 B 成功且读事务排空后，才可产生 `done`。任意一条带都不单独发布。

普通 [DMA测试](../sim/dma/verification.json) 实跑四模型、三输出槽、模式/源地址/输出bank在启动后的锁存、每个接缝和边缘、RRESP/提前RLAST/BRESP错误以及下一帧恢复。独立 [压力测试](../sim/dma_pressure/verification.json) 增加 AW 的 55/97 周期阻塞、W 的 41/89 周期阻塞、B 延迟 97clk，并把错误推迟到至少发生两个写事务之后，以覆盖已积累输出时的退出。压力用例尺寸为256×40，验证错误处理；其中的小尺寸fps不代表720p吞吐。

## 5. 完整帧调度与显示解耦

三原图槽继续用于采集、最新完整帧和 CNN 锁帧；CNN 在全部条带期间使用同一个源帧，最后真实 B 后才释放源。三输出槽为 0、2、10MiB，原图为 4、6、8MiB，每帧 1843200 字节。

沿用已验证的三输出槽调度：正在计算、已完成待显示、正在显示分别持有槽；两个完整帧队列条目保证顺序。`engine_done` 仅表示计算/DDR写入完成，显示 `commit_ack` 还要等待旧读事务、FIFO清空和安全消隐。**不能因为 reader 已提前更新 front_bank 就重用旧前台。** 这样 HDMI 换帧不再强制阻塞下一次 CNN 启动。

这也可以解释用户观察到的参考工程约20fps：原控制器等待 `commit_ack` 才允许下一作业；40.65ms计算时间超过两个60Hz显示周期，若每次都等下一个消隐，容易落在三个显示周期、约50ms一次的节拍，即20fps。**这是根据代码和周期关系的推断，不是本轮读取板上日志确认的结果。** 即使把CNN改到37.14ms，若仍将计算与显示串行，也可能仍落在同一个50ms节拍，因此不能只优化卷积、忽略提交调度。

本工程未实现左右对比和图像手势识别。若以后直接显示原图，必须另外增加原图显示引用/配对源帧的所有权，不能把当前 CNN 源锁直接当成显示锁使用。

## 6. DDR 预算、资源和最坏情况

外部 DDR/UI 时钟和板级电平均保持原配置。本轮未通过提高 DDR/UI 频率争取性能；约166.667MHz独立CNN、100MHz UI、720p60 HDMI仍分开计时。

风格从47种缩到4种后，参数 ROM 从 57152B 缩至 4864B，减少 52288B。每帧仍只处理一个锁定模型，所以这主要释放存储，并不直接按47/4倍加速。两份PW上下文和128bit环形槽会增加少量寄存器/多路选择。最终RAM、DSP、XLR及setup/hold以本工程同次 [signoff.json](../build/720p/signoff.json) 为准；单看MAC数量或原工程资源空余，不能宣称新工程已经布局布线通过。

以摄像头30fps、CNN30fps、HDMI60Hz计算：

| DDR流量 | 计算量 |
| --- | ---: |
| 采集写 | 55.296MB/s |
| CNN输出写 | 55.296MB/s |
| HDMI读 | 110.592MB/s |
| CNN源读，含当前突发过取 | 154.8288MB/s |
| 合计 | 376.0128MB/s |

源读不能只按1.5倍halo面积估算：每个缓存突发覆盖128像素，中心128/halo32的192列条带每行首尾各读2个突发，中间8条各读3个突发，共28×256B=7168B。每帧源读5160960B，是整幅RGB565帧的2.8倍。以上为当前地址序列的计算预算，不是实际DDR带宽测量；后续可通过跨条带缓存复用、改变条带宽度或更合适的突发范围减少过取。

虽然总字节量低于 DDR800×16bit 理论1.6GB/s，但控制器效率和事务延迟仍可能限制帧率。采集30fps和CNN30fps合计每秒6912000个单拍写事务；100MHz UI平均每个事务只有约14.47clk。共享写仲裁允许采集和CNN各一个在途，以重叠部分延迟，但不能推导出任意最坏B延迟下仍不丢帧。97clk延迟测试证明了背压/错误处理安全，并未证明这种服务速度能支撑720p30。

## 7. 如何验收真实30fps

当前35.48fps模型成绩相对30fps目标留下约15.4%的时间余量，但还必须完成真实采集、DDR、CNN和HDMI长期并发验证。

- C：完整采集并等待最后DDR B后发布的帧数；I：`engine_done && !engine_raw` 的真实CNN完成帧数；H60：HDMI刷新配置。原画复制和重复显示不计入I。
- 固定同一风格运行至少数十秒，用累积完成帧数之差除真实时间，记录采集/推理/显示错误、跳过源帧、FIFO溢出及画面。不要只看某一秒的I30。
- 检查新推理源帧编号持续前进、同一源帧不被重算冒充新帧，输出只能在完整提交后显示。
- 切换四种风格和回到原画，核对忙中请求、权重装载、模型身份、异常退出与恢复。运行中配置不得覆盖正在推理的参数。
- 保留板级供电、接口电平、电流和温升的实际检查。仿真/时序审查不能保证模拟电气环境零风险。

新bit的生成和签核不代表已经下载，更不会改变旧Flash启动内容。本页不记录未执行的实板30fps验收结果。

## 8. 不能省略的原生网表数值复查

本轮曾出现“RTL仿真正确，实际映射后的数值错误”：初版用 `result[context][channel*8+:8]` 和 `output_queue[slot][lane*16+:16]` 动态二维部分写。独立Efinity原语模型回归发现，单核第一个像素与参考不同；DMA的原画旁路也出现首个非零像素变成零。

这不是仅凭屏幕颜色猜测：只读网表可见部分AXI数据lane被连接为常零。进一步轨迹证明原画模式已正确锁存，fast FIFO输入/输出非零且相同，而拼包后的lane稀疏、位置错误。因此不能靠调整Bayer、修改权重或放宽数值判据掩盖问题。

修复采用固定位置的generate写者：每个PW context/channel、输入context和输出队列slot/lane分别拥有常量索引写入；上下文指针、队列握手、位宽和运算顺序保持相同。主always中的旧数组写入和整数组reset相应移除，避免多驱动。固定PW候选已经在原生网表中逐值通过四组学习参数共3840个像素；固定DMA候选的实际原语网表也完成四种256×40整帧、三输出槽、读写背压、最终B、错响应恢复及原画旁路恢复，全部通过。

固定写者源码随后逐字节复制到生产目录，生产路径的四风格完整720p和模块回归全部重新执行。若原生DMA网表使用候选路径编译，最终来源记录必须同时保留原始候选编译输入、原始PASS日志以及 `production_aliases`：分别记录候选和生产的实际路径/指纹，并重新读取二者证明字节一致。**不能只把候选收据里的路径文字替换为生产路径，不能把旧动态候选的STA或网表用于新生产签核。** 最终生产整机仍独立重新综合、布局布线和STA，单核也重新映射/数值核对。

初版失败候选保存在本地 `build/baseline_dynamic/`，诊断日志只用于说明这次发现。最终收据必须绑定实际生产源、同次原语网表、真实日志和全部模型参数；`signoff.json`只接受这些一致的证据。RTL通过、资源放得下和STA通过缺一不可，任意一项都不能替代映射数值回归。

## 9. 保留的下一步实验

只在独立仿真目录试跑了中心256、左右halo32、总宽320的五条带方案。梵高完整720p输出误差0，2661739个UI周期，约37.57fps；这是一个模型的RTL/CNN/DMA实验，未做该尺寸实际综合/时序，也未采用为当前生产配置。当前单拍B服务已成为较明显限制，条带加宽虽然减少重复计算和源读过取，收益仅约5.9%，因此本轮保持已经验证的中心128参数。

如果实际板上并发仍达不到30fps，优先考虑将CNN每行的中心128像素合成16个AXI128数据拍、一次写突发。当前每行中心区正好256B对齐，合法地不跨4KB边界，理论上可将每帧115200个单拍写事务减少到7200个16拍事务。此项尚未实现，必须一并修改AWLEN/WLAST、共享写仲裁、缓冲与完整帧/最后B的验证，不能直接修改某个端口常量就作为完成；本轮没有以它的理论预算宣称额外帧率。
