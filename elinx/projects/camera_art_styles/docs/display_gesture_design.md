# 显示模式、手势切换与帧缓冲设计

日期：2026-10-23。本文以已签核的 `build/camera_720_fast/` 为现状基线，提出后续交互设计。**本文中的新显示、手势识别、寄存器和帧池方案尚未接入生产工程，也没有新交互版 bit。** 当前独立完成的代码仅为第8节的四秒稳定门控模块。

用户本轮优先事项是提高真正的风格推理帧率；同意另训轻量学生，先对照画质再选型。因此本设计不改已签核源清单、模型、固件、约束、引脚、电平和 bit，也不以交互功能替代帧率优化。

## 1. 用户交互目标

按键负责显示内容，手势只负责选择风格，两者分开。

| 项目 | 约定 |
| --- | --- |
| 原图界面 | 实时显示完整、已发布的摄像头原图；允许检测手势 |
| 风格界面 | 显示最近完整风格化帧；关闭手势取样与资格计数 |
| 对比界面 | 左640列原图、右640列风格图，必须来自同一源 `frame_id`；允许检测手势 |
| 手势1 | 梵高厚涂，模型槽0 |
| 手势2 | 彩色剪纸，模型槽1 |
| 手势3 | 复古漫画，模型槽2 |
| 手势4 | 水墨，模型槽3 |
| 手势5 | 没有此项，用户已澄清只用1–4 |
| 触发要求 | 同一有效手势持续满足4个完整的一秒窗口后，发出一次风格请求 |
| 重复触发 | 手一直保持时不重复；确认无手、重新伸手并再次满足4秒才可触发 |

手势改变模型身份，不自动改变显示界面。比如在对比界面完成手势2，仍保持对比界面，等剪纸的新配对帧准备好后，在安全消隐时整帧切换。原图界面识别到手势时，原图可以继续实时显示；风格结果在后台完成，用户再按键查看。

建议按键新分配如下。它是待集成方案，**现有 bit 仍是旧四键选风格操作**。

| 板上按键 | 建议功能 |
| --- | --- |
| KEY0 | 请求原图界面 |
| KEY1 | 请求风格界面 |
| KEY2 | 请求左原右风格界面 |
| KEY3 | 保留调试/叠加开关，暂不定义风格选择 |
| KEY0+KEY3长按 | 保留现有约1秒逻辑复位 |

按键继续两级同步、约10ms消抖、释放后再武装和长按去重。组合复位键出现时抑制单键请求，避免先切界面再复位；新交互版不能继续沿用旧 `style_keys_view` 中 KEY1+KEY2 回原画的组合含义。

## 2. 当前实现为什么不能直接换几个按键

实际源文件为：

- `rtl/p720/video_system_720.sv`：连接原画采集、RISC-V/APB、引擎、读写仲裁和显示。
- `rtl/view/style_keys_view.sv`：单键既选择模型，又将 `raw_mode` 置0；组合键将 `raw_mode` 置1。
- `rtl/p720/video_tile_engine_async.sv`：按整帧作业锁存 `raw_mode`。它决定做CNN，还是把原图复制到输出bank。
- `rtl/source_frame_pool.sv`：三个原画bank，只有一个 `engine_owned` 推理锁。
- `rtl/video_job_control.sv`：`engine_done` 后立即 `release_source`，等待显示提交时只保护输出bank。
- `rtl/frame_reader.sv`：`front_bank` 只有1位，读基址只能是0或2MiB。
- `rtl/hdmi60/video_raster60.sv`：只消费一条完整RGB565像素流，不认识原画/风格双地址。
- `rtl/p720/video_control_apb_fast.sv`、`firmware/main.c`：CPU根据 `requested_style` 加载权重并逐帧START。

当前“原画模式”走的也是锁源、DMA复制、最后DDR B、输出提交流程，并不是摄像头最新原画直接送显示。改变旧 `raw_mode` 会改变加速器实际工作，不能把它直接当成新的 `display_mode`。

必须新增相互独立的概念：

| 状态 | 意义 | 建议归属 |
| --- | --- | --- |
| `display_request` | 用户想看原图/风格/对比 | UI域控制寄存器 |
| `display_active` | 已在安全消隐实际生效的界面 | reader前台描述符 |
| `requested_style` | 下一次期望加载的模型 | CPU/APB控制 |
| `loaded_style` | 已完整加载且收到实际CNN配置确认的模型 | 现有控制器 |
| `job_style` | 本次整帧推理实际使用的模型 | 作业锁存 |
| `job_frame_id` | 本次处理的源帧号 | 帧池/作业锁存 |
| `diagnostic_raw_bypass` | 显式调试时才使用的原画复制旁路 | 引擎调试配置 |

正常风格推理固定走CNN。按键更改显示界面，不得在运行中把正在处理的帧改成原画，也不得修改已锁存的模型。CPU可以忙时保留最新模型请求，等当前作业结束再换权重；禁止边处理边覆盖当前唯一权重集。

## 3. 三种显示模式的时间关系

### 3.1 原图界面：最新完整原图

原图应选择最近一次完整捕获、最终DDR写响应成功的原图帧，并在显示安全消隐窗口获取显示引用。正在捕获的半帧绝不能成为显示源。

摄像头约30fps而HDMI为60Hz时，一张原图通常重复显示两次。用户看到流畅原图，并不表示CNN变为30fps或60fps。

原图界面中手势检测的数据来自持续更新的摄像头预处理支路，不能从同一张停留四秒的显示快照反复读取并假装检测了连续视频。

### 3.2 风格界面：最近完整推理结果

只在整帧全部条带、所有输出DDR B以及安全消隐条件满足后更新。CNN若只有约1.88fps，HDMI仍每秒扫描60次，但多数扫描重复同一风格帧。

风格界面关闭手势识别取样请求和稳定资格计数。摄像头本身仍持续服务，不能为了停手势就停止MIPI输入或不处理无背压数据。

### 3.3 对比界面：配对帧，不能左新右旧

左半原图必须是右半风格画的**那一张源图**，即两边 `frame_id` 一致。右侧更新为新风格结果时，左侧原图同步切换。不能左边用30fps的最新原图、右边用旧的1.88fps结果来做未标注的“处理前后对比”。

因此对比画面本身以推理速度更新，左侧也会暂时冻结。手势检测仍可由显示之外的实时预处理支路采集，以免冻结的对比左图导致识别样本失去时间连续性。应在UI上明确“配对原图”，并分别显示实际采集、推理与手势检测更新信息。

没有有效配对结果时，显示“等待风格帧”的原图界面或占位画面。不要用不同帧拼接填满屏幕。进入对比后取得完整配对前，实际状态仍不是有效对比，手势门控应按已显示状态决定是否开启。

## 4. DDR地址与所有权

### 4.1 已有地址

一帧1280×720 RGB565为1,843,200字节，即 `0x001C2000`，每行2560字节。每个槽位间隔2MiB，当前地址如下：

| 当前槽位 | 基址 | 用途 |
| --- | --- | --- |
| 输出0 | `0x00000000` | 风格/原画复制输出 |
| 输出1 | `0x00200000` | 风格/原画复制输出 |
| 原图0 | `0x00400000` | 动态采集/最新/推理角色 |
| 原图1 | `0x00600000` | 同上 |
| 原图2 | `0x00800000` | 同上 |

目前推理源完成后立即归还帧池；把reader改为读该地址并不能继续保护它，后续摄像头可能覆盖仍在显示的源图。这会造成画面撕裂、左右帧不一致，属于所有权错误。

### 4.2 推荐：扩展原画槽位并增加引用角色

优先利用外部DDR，增加两个原画槽位，不增加完整帧片内RAM，也不为对比额外复制整张原图。

| 建议新增槽位 | 基址 | 帧数据结束地址（不含） |
| --- | --- | --- |
| 原图3 | `0x00A00000` | `0x00BC2000` |
| 原图4 | `0x00C00000` | `0x00DC2000` |

这些是**候选地址分配**，尚未接入DMA。集成前要核对当前DDR控制器可访问容量、地址位宽及其它master的使用范围，不能只因地址低于30位就假定可用。

最坏同时存在五个不同原图角色：

1. `capture`：摄像头正在写的原图，写入未完成。
2. `latest`：最近完整、尚可被推理/手势/预览选用的原图。
3. `engine`：CNN正在读的源图。
4. `live_front`：当前原图界面正在从DDR读的原图。
5. `pair_front`：现有风格前台对应的原图，保留以便随时进入对比。

某些角色可以引用同一bank，比如推理选中的正好是当前预览帧，但不能依赖这种巧合来计算最坏容量。若增加一个独立DDR手势读者，它也需要引用和释放，可能再增加最坏占有；推荐手势直接从预处理支路取低分辨率图像，避免额外整帧DDR读者。

用每bank角色位掩码或受控引用计数替代单一 `engine_owned`：

```text
CAPTURE | LATEST | ENGINE | LIVE_FRONT | PAIR_FRONT | PAIR_PENDING
```

`PAIR_PENDING` 是从 `ENGINE` 原子转交的角色；同一作业等待提交时不再有另一活动引擎源，因此不是额外第六张图。开始下一作业前先完成待提交配对的转交或丢弃，保证占有上界。

分配器只允许在没有任何读引用、不是最新保留帧、不是采集目标的bank上开写。同拍claim/publish/前台释放必须先算下一状态，再统一更新，避免两个控制分支分别覆盖引用位。

### 4.3 必须更改的释放时机

```text
源claim
  -> ENGINE引用
  -> CNN完成且最终写B成功
  -> ENGINE原子转成PAIR_PENDING
  -> 同一安全消隐提交{raw_bank, style_bank, frame_id, style_id}
  -> 新PAIR_FRONT生效
  -> 排空旧显示读事务后释放旧PAIR_FRONT
```

`engine_error` 时释放本作业的ENGINE引用，不发布新pair。新的配对没有提交前，旧配对保持完整有效。

显示reader从AXI DATA退回无在途事务状态后，才可释放旧原图引用；切换时还应重置像素FIFO，避免旧帧尾部混入新帧。跨域请求晚到有效区时依旧等下一次受保护的消隐窗口，不能仅看到换帧请求就提交。

全局复位/PLL失锁/DDR校准失效应清空所有在途描述符和所有权；不能保留一个看起来valid、实际DDR内容已不可依赖的前台。局部界面切换只释放对应读引用，不得复位正在进行的摄像头整帧写入。

### 4.4 若只扩到四个原图槽位

四槽可支持 `live_front + engine + latest + capture`，但必须在原图界面释放旧风格配对原图；从原图切到对比时等待新配对产生，期间禁止再启动会增加占有的新作业。这样可以减少槽位和控制状态，但不能宣称即时保留原有比较结果。

继续只用现有三槽并同时长期锁住显示原画与推理源，会减少或阻断采集可用槽，增加丢帧，反而不利于用户提高帧率的目标。

### 4.5 备选：额外保存配对原画快照

也可给两个风格输出分别增加对应原画快照槽，先复制源图、再计算风格；两者都成功后联合提交。这样不必长期占用采集槽，但每次增加一帧源读和一帧原图写。720p每次额外搬运3,686,400字节，且增加复制延迟、DMA调度与错误恢复状态。

帧率优先时先选引用保护方案，避免把现有 `raw_mode` 原画复制和CNN串行执行当作免费的显示功能。

## 5. 单FIFO的分屏reader

推荐仍只使用现有128→16位异步像素FIFO，UI域reader按显示顺序选择DDR地址，不在像素域新建两套大FIFO。

### 5.1 像素地址

完整源图和风格图仍都是1280×720，按相同坐标展示：

```text
原图：      address(x,y) = raw_base   + y*2560 + x*2
风格：      address(x,y) = style_base + y*2560 + x*2
对比左侧：  x < 640      -> raw_base   + y*2560 + x*2
对比右侧：  x >= 640     -> style_base + y*2560 + x*2
```

这表示左边是整张图的左半，右边是同张图的右半，不把两张完整图分别压扁成640列。边界处物体位置连续，只在纹理风格上发生变化。

现有AXI读突发16拍，每拍128位，一突发256字节，等于128个RGB565像素。640列正好5个突发，每行左右各5个，总计仍10个突发、720行共7200个，与单画面相同。每行2560字节也是256字节整数倍，不需要跨源突发。

原图/风格/对比三种模式在像素流中都正好输出921,600个像素，FIFO和TMDS链路无需感知双源地址。不能先向FIFO塞入整幅原图，再在像素域“跳过一半”来拼接；那会改变消费量并使行偏移。

### 5.2 原子前台描述符

建议reader锁存：

```text
mode、raw_base、style_base、raw_frame_id、style_source_frame_id、style_id、valid
```

对比模式只接受 `raw_frame_id == style_source_frame_id` 的完整描述符。所有地址和模式在一次显示帧内保持不变，不允许前半行读旧原图、后半行读新风格。

UI域做地址选择后，像素域只接原有像素FIFO、有效帧标志和请求/ACK。需要给像素OSD显示模式或风格号时，用稳定数据握手/完整快照转交，不直接采样多位UI寄存器。

### 5.3 复用与新增验证

保留 `frame_reader` 的RRESP/RLAST检查、遇错整显示帧作废、垂直消隐重置FIFO和下一帧恢复。新增左右地址接缝、行号/列号、最后一突发、输出顺序和原画bank释放检查。

原图显示的理论有效DDR读量为1,843,200×60=110,592,000字节/秒。摄像头30fps原画写约55,296,000字节/秒，另有CNN条带halo重复读写和仲裁开销。这些是数据量预算，不是实测DDR带宽。对比分屏本身不需双倍读量；若实现为两帧全读后丢一半，才会白白加倍。

## 6. 手势检测究竟由谁完成

目前工程没有真正的1–4手势分类器。现有CNN是绘画网络，不会因增加一个计数器就自动识别手指数量。

可选路线如下，尚未选定最终模型或训练数据：

| 路线 | 实际需要实现 | 适用边界 |
| --- | --- | --- |
| FPGA预处理+RISC-V分类 | 从RAW/RGB支路生成低分辨率ROI/掩码；CPU得到一张原子快照，分割手部并提取或分类1–4 | CPU目前无DDR搬图主口，需独立APB快照/流式特征口；不能直接在旧固件中读整张DDR图 |
| 小型手势网络 | 建立1/2/3/4、无手、未知类，做留出测试和量化，分配MAC/存储/调度 | 当前RAM254/256、DSP148/160，不能直接塞入第二个大网络；先与风格模型资源优化一起评估 |
| 传统手部轮廓/指峰 | 真实摄像头图像分割、连通域、轮廓或凸缺陷等得到手指计数 | 可做辅助交互，但须测试肤色、背景、光线、手势方向；不能把“检测到肤色区域”称为识别1–4 |
| 主机识别 | 主机取得与板载摄像头对应的新图，再发经过协议定义的识别结果 | 需要额外图像传回/主机依赖，不是当前离线板上功能，也不把PC另一摄像头的结果当作同帧识别 |

推荐先以采集支路的低分辨率图像做识别输入，独立于慢速风格结果。分辨率、ROI、置信度阈值、类别定义要通过真实手势数据确定，不凭空保证64×48或96×96足够。

工程需提供每条识别结果的 `sample_frame_id` 或等效递增序号。重复读取同一帧不构成新的 `sample_strobe`；计数器回卷和丢帧也需按定义处理。输入图像过旧、CSI/DDR源故障、检测超时、置信度不足或多手冲突都要输出无效，不能保持上一标签假装继续检测。

暗环境正是当前现场问题之一，分类器需要包含暗场、无手和误检对照。尚未取得真实混淆矩阵、误触率或板上耗时时，不能声称手势识别已经完成。

## 7. 四秒判定语义

### 7.1 四个完整窗口

资格计时从首次有效新识别报告开始，而不是从任意系统1Hz边沿开始。每个窗口持续100,000,000个UI周期，即在100MHz下为一秒。

```text
首次报告 A       窗口1结束       窗口2结束       窗口3结束       窗口4结束
t=0              t=1秒           t=2秒           t=3秒           t=4秒
|------ A --------|------ A --------|------ A --------|------ A --------|
                                                                  发一次请求
```

如果分类器恰好每秒报告一次，需要t=0/1/2/3/4的五个观测来支持四秒经过；在t=3秒不能因为已经看到四次标签就提前切换。检测器应尽量在每秒窗口内提供更多真实新帧，例如5–10次/秒，以便捕捉窗口内部的手势变化；具体频率必须由性能测试决定。

每个完整窗口都要至少有一次该手势的真实新报告。检测器报告间隔超过看门狗、报告了另一手势/无效/无手，或显示资格被关闭时，已完成窗口全部清零。边界上的报告属于刚结束的窗口，不同时算给两个窗口。

### 7.2 模式门控

`gesture_enable` 根据**实际已显示**的原图或对比界面产生；不能仅使用按键请求值，因为显示切换要等待安全消隐确认。

任何界面实际切换应给资格门控一个 `cancel`，包括原图→对比这类两侧都允许识别的切换，以避免把两段不连续观察拼成四秒。风格界面不采样，已积累资格也不保留。

触发后保持“已触发锁定”。改成另一个有效手势、切界面或给一条不确定结果都不能解除锁定；要在允许检测的界面确认无手，再开始新的四秒。

当前独立模块用一条明确的 `sample_no_hand && !sample_valid` 报告解除锁定。真实识别器应先对“无手”做可靠确认；若单帧抖动会误判无手，应在识别前端加释放稳定门限。模块本身未加入额外的无手持续时间。

### 7.3 采样和时间的边界

离散摄像头无法证明两个观测之间手势在物理世界绝对不变。“连续”表示在规定采样频率、新鲜度和全部已观测有效结果下持续成立。文档和测试不能把100MHz计数器当成每秒一亿次真实图像识别。

检测器时钟不在UI域时，应通过异步FIFO或稳定邮箱整体转交 `{frame_id, valid, no_hand, id, confidence}`；不能逐位同步多位手势编号。报告载荷与strobe必须属于同一次识别。

## 8. 已实现的独立门控模块

源文件：`rtl/interaction/gesture_hold_gate.sv`。未加入任何已有工程XML或顶层。没有引脚、PLL、DDR、CPU、训练模型或bit改动。

### 8.1 参数

| 参数 | 默认值 | 含义 |
| --- | --- | --- |
| `WINDOW_CYCLES` | 100000000 | 每个完整窗口的时钟数，必须>=1；默认UI100MHz下一秒 |
| `MAX_REPORT_GAP_CYCLES` | 100000000 | 距上一有效同类报告允许的最大周期间隔，必须>=1 |

看门狗默认允许1Hz边界到达的新报告。若识别器稳定达到10Hz，可在后续工程中按实测延迟把最大间隔缩短，例如0.3秒，但这不是本模块已验证的实板识别频率。

### 8.2 端口

全部信号属于 `clk` 域。

| 端口 | 方向/位宽 | 定义 |
| --- | --- | --- |
| `clk` | 输入1 | 时间资格计数时钟，拟接UI100MHz |
| `reset` | 输入1 | 同步高有效复位；清空资格，重新武装 |
| `enable` | 输入1 | 实际界面允许检测且源有效 |
| `cancel` | 输入1 | 模式变化/采集异常/时间基准异常取消本次资格 |
| `sample_strobe` | 输入1 | 一条新的、已经原子转交的识别报告；不能重复同一帧 |
| `sample_valid` | 输入1 | 报告是高置信度的有效手势1–4 |
| `sample_no_hand` | 输入1 | 明确确认无手；不等同于低置信度未知类别 |
| `sample_id` | 输入3 | 手势1/2/3/4；0及5–7作无效 |
| `switch_valid` | 输出1 | 第四完整窗口完成时的单周期脉冲 |
| `switch_style` | 输出2 | 已确认模型槽0/1/2/3；与switch_valid同拍有效 |
| `candidate_id` | 输出3 | 当前资格候选；0表示无候选 |
| `completed_windows` | 输出3 | 已完成0–4个完整窗口，供进度叠加 |
| `armed` | 输出1 | 1表示可接受新的四秒资格；0表示已触发、等待确认无手 |

`sample_valid` 与 `sample_no_hand` 同时为1是矛盾报告：按无效处理并清资格，不作为释放。没有strobe时其余输入不产生一条报告；旧标签不会自行保活。

第四窗口的触发报告当拍若同时出现 `cancel`、失去enable、无效报告或新手势，取消/重启优先，不允许旧手势触发。

本地脚本：`sim/interaction/check_gesture_hold.py`。用独立的绝对时间戳、最后报告时间和每窗口报告集合构建参考，与RTL逐拍对照；不直接复制RTL计数状态机作为参考。

| 窗口周期 | 最大报告间隔 | 测试周期数 | 合格触发次数 |

| 8 | 3 | 13226 | 12 |
| 8 | 8 | 13260 | 13 |
| 5 | 100 | 12880 | 13 |

共63,758个时钟周期一致，覆盖四类到槽号映射、完整4窗口而非3秒、边界报告、1周期参数、候选切换、无效ID、不确定结果、无手、检测停止/看门狗、漏窗口、enable/cancel、触发后保持与改手势不重复、确认释放后重武装，以及每组12,000拍随机输入。

## 9. RISC-V/APB后续接口建议

现有自定义窗口基址 `0xF8100000`，最高现有已知寄存器为偏移0x60。以下偏移仅是规划，集成时先检查是否与其它新功能冲突；**当前bit访问这些偏移会报未知地址错误**。

| 建议偏移 | 名称 | 用途 |
| --- | --- | --- |
| `0x64` | DISPLAY_REQUEST | 0原图、1风格、2对比；请求而非当拍生效 |
| `0x68` | DISPLAY_STATUS | 实际模式、待切换、有效配对、缺帧/显示故障 |
| `0x6C` | GESTURE_CONTROL | 使能、显式清资格；禁用不改变摄像头采集 |
| `0x70` | GESTURE_RESULT | 最近真实报告的类别、valid/no_hand、置信度摘要 |
| `0x74` | GESTURE_STATUS | 候选、完整窗口数、armed、过期/丢报告计数 |
| `0x78` | LIVE_FRAME_ID | 当前原图前台源帧号 |
| `0x7C` | PAIR_FRAME_ID | 当前完整配对源帧号 |
| `0x80` | STYLE_STATUS | requested/loaded/job/front模型身份 |
| `0x84` | GESTURE_SWITCHES | 真正通过四秒门控的累计请求次数 |

手势门控 `switch_valid` 只写“期望风格”或一个新的中断事件。CPU仍负责权重加载/确认、START、完成中断，不得把手势脉冲直接连到CNN START绕过权重身份与源有效检查。

建议软件流程：

1. 按现有顺序完成ID/配置读回、权重加载和摄像头开流。
2. 收到显示按键请求，写显示请求；实际reader确认后再更新手势enable/cancel。
3. 真实识别前端交付新报告，门控硬件累计完整窗口；若由CPU提供报告，APB写入必须整体成事务。
4. 四秒通过后记录目标模型。当前作业忙时只保留最新合法请求，不改正在运行的模型。
5. 当前作业结束、无未交接提交后，按 `load_target -> LOAD_BEGIN -> 1217项写入 -> 最后跨域ACK -> COMMIT` 加载旧模型；若最终选用了轻学生，参数数量和地址序列另设版本，不能继续硬写1217。
6. 对最新完整源帧发START，锁源帧号与模型；失败保持旧前台，释放本次引用。
7. CNN整帧成功后联合提交同源raw/style描述符，保留用户当前显示模式。

RISC-V C修改仍按当前Git范围留本地，不擅自改变上传白名单。后续新bit须包含对应的新固件/四路boot RAM，不把仅改C文件当成已运行的新控制逻辑。

## 10. 帧率与资源边界

当前完整720p梵高RTL/DMA测试为53,156,739个100MHz UI周期，等效约1.881fps；HDMI是60Hz，预期摄像头采集约30fps。该数是仿真算出的完整作业吞吐，不是新720p实板测量。

原图改成直接显示最新完整源帧可以明显改善观察流畅度，也能使手势检测不受慢CNN更新限制，但**不会提高CNN真实FPS**。对比模式若严格同帧配对，画面更新仍受CNN限制。

提高推理帧率需要单独解决通道复用、卷积流水、halo重复、模型规模与存储时序。当前RAM254/256、DSP148/160，不能把显示分屏/第二识别网络看成资源免费。优先：

1. 按实测完整作业周期拆分计算、DMA、条带重叠和提交等待。
2. 对同一模型做数值完全一致的吞吐优化；不能靠放宽时钟约束或提高DDR/UI频率掩盖问题。
3. 按用户授权另训轻量学生，保留旧模型，对同图同曝光输出做画质比较后再决定。
4. 在选定架构中安排低分辨率手势前端，并验证与采集/显示/推理并发的最坏资源和带宽。

最终诊断分别给出：采集好帧C、CNN完成I、HDMI扫描H、真实新手势报告G、手势有效率/过期计数、对比配对帧号、显示欠载、DDR错误和因所有权/忙主动丢弃的帧。不能把原图30fps或重复风格60Hz称为已达到风格推理15fps。
