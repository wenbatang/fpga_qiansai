# 真正720p风格转换：重叠分条

本项目解决Ti60片上CNN行缓存随整图宽度增加而超限的问题。输入和输出均为1280×720，四种原模型与量化参数保持不变；显示按用户要求720p30。原`uart_style_keys`工程与已签核bitstream保留。

## 算法与硬件工作流

五层卷积膨胀率为1/1/2/4/8，感受野半径16、宽度33。把整图横向划成四条，每条保留320列，左右各加16列上下文，CNN固定处理352×720。条起点为-16、304、624、944；只保留每条局部x=16..335，写回整图x=0..319、320..639、640..959、960..1279。

| 条编号 | 实际CNN输入的全局x范围 | 保留并写回的x范围 |
|---|---|---|
| 0 | -16..335 | 0..319 |
| 1 | 304..655 | 320..639 |
| 2 | 624..975 | 640..959 |
| 3 | 944..1295 | 960..1279 |

不存在的全局像素在每一层都清零。仅在RGB输入补零会让隐藏层偏置产生边界外特征，导致边缘与整图计算不同。X/Y模4特征使用全局坐标，不能在每条里随意重置。FPGA输入仍只有RGB565，不增加串口特征数据。

1. COBS/CRC接收1280×720 RGB565原图，完整写入DDR 0x00400000。半帧不参与推理。
2. `style_tile_engine`锁住风格与后台bank，启动第0条；整幅图期间保持写所有权。
3. 按行读DDR中与当前条相交的128像素块。每次16拍×128bit，共256字节；固定生产尺寸的行stride是2560字节，地址256字节对齐，不跨4KB。缓存整段R响应后才交给CNN，错误段不可作为有效缓存。
4. `style_cnn_tile5`仍同时运行五层、六通道、144个DSP，只有行宽从整幅图变成352；逐层掩掉全局边界外特征。
5. 每条舍弃左右重叠结果，将中间320列按整图stride写回后台。八个RGB565像素组成一个128bit写拍，AW/W各自握手，等待B响应。
6. 当前条全部输入/输出、CNN done、最后写响应都完成后，复位本条计算状态，启动下一条；不会把某一条当作完整帧发布。
7. 四条全部完成后通知现有控制器，显示仍等安全垂直消隐再交换bank；此后才发UART END ACK。忙时只保留最新按键请求，按键作业不伪造串口ACK。

读写地址/VALID在背压期间保持不变。RRESP、RLAST、BRESP错误停止新计算，并排空已经承诺的AXI事务，错误后台不发布。读缓存使用少量寄存器，避免为此新增大块BRAM；原DDR控制器与显示异步FIFO保留。

## 两个配置

- `720p`：默认1280×720输入/输出，四条352×720计算，720p30满画布显示。
- `vga`：显式640×480输入/输出，两条352×480计算，720p30居中显示。用于后续优先验收赛题640×480实时推理；不是静默降低默认720p。

两配置各自保留工程、`style_profile.vh`尺寸宏、权重路径和签核文件，公共RTL相同。生成另一个配置不会改前一个配置的宏或权重路径。模型不在本轮重训。

## 验证范围

- `sim/check_tiles.py`：128×24缩小几何、四种真实模型；逐像素与整图整数参考一致，检查全部条接缝、图像边缘、全局坐标、读写背压、最后B屏障、RRESP/提前RLAST/BRESP故障和恢复。
- `sim/check_link.py`：真实四模型与COBS/CRC包、同步包RAM、DDR、按键、完整帧发布联调；一次上传多次换风格，忙BEGIN保留源图，ABORT/半帧失效、重复END不重复推理，错误后台保留旧前台。
- `sim/check_full_reference.py`：完整1280×720与640×480、四种风格，RGB565量化后分条和整图软件整数输出最大误差均为0。它验证完整尺寸数学结果，不是完整尺寸RTL吞吐或上板FPS。
- `sim/check_video.py`：独立完整720p30时序、居中VGA/下溢恢复；720p满画布读取另行覆盖。`check_fifo.py`、`check_tmds.py`与`check_camera.py`检查新项目副本与GUI。
- 完整综合、接口、布局布线、STA、66个实际封装引脚及电平核对，来源/模型/权重/配置/bitstream绑定同次记录。实板结果另外记录。

## 与最终赛题的关系

分条解决缓存容量，仍会增加重复计算和DDR读取。每帧实际输入计算像素为4×352×720=1,013,760，较720p裸像素多10%；管线启动、零padding、AXI响应和显示仲裁另计。它不是通过放大VGA来假装720p，也不能据此宣称720p处理30fps。

本轮UART仍停等传原始像素，2Mbps的720p裸数据预算9.216秒；十秒完整上传需实测END ACK总时间。后续用MIPI替换慢速输入，优先在VGA配置验证采集≥30fps和推理>15fps，再扩展720p实时处理。即使缓存已能装下，720p计算吞吐仍需进一步流水化或独立更快CNN时钟；不能提高DDR控制器UI时钟来冒险提速。
