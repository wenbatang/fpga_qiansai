# 为什么更少参数仍要重新设计硬件

本次目标是完整1280×720、每秒30张不同的风格图，帧预算33.333ms。降低参数量是手段，吞吐、片内存储和DDR调度必须一起满足预算。

## 算术量与参数量分开看

新网络每像素执行stem的18个、四组DW/PW的4×(54+36)个、head的18个MAC，共396MAC。没有把激活、加残差、舍入或地址生成计作MAC。完整720p为364953600MAC/帧，30fps约10.95GMAC/s；四条halo额外运算约10%，还需计入边界和流水填充。

保留C8模型每种风格784个卷积权重，但其CNN分支每4个原图像素只处理一个特征像素，因此约196MAC/原图像素。恢复完整尺寸后，新C6虽然参数比C8少49.49%，每帧算术量仍约为原分支的2.02倍。不能只按参数数目推断帧率或资源下降。

## 实际采用的优化

| 瓶颈 | 新实现 |
| --- | --- |
| C8分支会降低空间分辨率 | 学生的stem改为1×1、隐藏通道6，全部层保持720p |
| DW一个tap顺序计算 | 三个列bank并行读三个tap，三行分时计算，内部区四拍一像素 |
| PW出通道串行 | 两个出通道并行、四个上下文，乘积/部分和/舍入/移位流水 |
| 反射坐标/取模/bank/RAM使能组合链过长 | 下一像素地址前瞻两级寄存，三个行基址在FEED提前寄存 |
| 边界三tap命中同bank | 单独第二读相位，真实计入吞吐，不假定任意位置三读无冲突 |
| 输出打包等待每次DDR响应 | 两个128bit打包槽，只有真实B才回收槽，允许另一槽继续打包 |
| 摄像头和CNN写入互相完全串行 | 两写主各一笔、合计两笔在途，按序路由B并归还信用 |
| 计算结束后还串行等待显示消隐 | 三输出bank；前台、待提交、引擎分别拥有槽，reader晚ACK释放旧前台 |

最后两项主要减少空等，不会把重复显示算作处理。调度测试用12个不同30Hz源帧，并独立检查原图模式不增加I；真实CNN完整帧数值和调度模型分开验证。

## 720p与缓存

四条×320×720恰好921600有效输出像素，每条352×720包含左右16列halo。每层保持全局坐标和reflect101，所有条写同一个输出bank；任何一条失败都不能发布部分图像。分条改变计算次序、节省行缓存，不改变图像宽高或像素间距。

三原图bank保留采集、最新完整与推理锁帧；三输出bank保留前台、待提交与引擎。两组像素异步FIFO隔离100MHz UI和166.667MHz CNN。DDR仍采用已核对400MHz PHY，没有用提高DDR频率解决带宽。

## 吞吐证据及实际限制

最终四风格完整720p RTL/CNN/DMA约2558528个100MHz UI周期，即25.58528ms，最慢39.084974fps。与30fps预算相比，尚有约7.75ms/帧用于真实系统中的额外调度和存储等待。最终准确周期、时序和资源见[验证说明](validation.md)。

这是有界AXI背压条件下的功能仿真。真实DDR的竞争、读突发边界与单拍写响应延迟可能消耗这部分余量。摄像头采集、显示读取、源图读取和风格写入同时发生，外部存储实际效率需要上板观察，不能用理论带宽或仿真39fps保证实物30fps。

上板时先选择风格再读I，连续至少多秒看稳定值；同时记录C、捕获错误、推理作业错误/主动跳帧和显示欠载。启动原图的I为0属于正确行为，H60仅表示显示刷新配置。如果实际I低于30，优先用引擎周期和作业间隔区分计算慢还是DDR/调度等待，再决定是否做突发合并，避免盲目提高时钟。
