一张图片，如何从电脑
经过 UART 和 DDR3，走到 HDMI 屏幕？

电脑把图片转成 RGB565 原始像素，通过串口送入 FPGA。FPGA 将完整图片存入 DDR3 的后台缓冲，校验成功后在安全的显示边界发布；显示通路持续从前台读取像素，产生标准 720p60 视频时序。

02 / UART

串口基础：线上实际发送的是什么？

UART 是异步串行通信。双方约定波特率，发送端在 TX 上逐位输出，接收端从 RX 的起始位判断采样时刻。这里不传独立时钟，电脑经过板上的 CH340 USB-UART 桥连接 FPGA；发送图片和接收应答分别使用两根方向相反的数据线。

8N1：一个字节占 10 个线上的 bit

8 个数据位、N 表示无奇偶校验、1 个停止位，另外还有 1 个起始位。空闲为高；起始位拉低；数据按最低位先发；停止位回到高电平。

2,000,000 baud 时每位 0.5µs，每个字节至少 5µs，最大原始字节速率约 200,000B/s。115200 baud 时最大约 11,520B/s。

波特率、分包大小是两种设置

波特率决定每个位有多快，必须与 FPGA 的 UART_BAUD 相同。分包大小决定一次停等事务里放多少像素，必须不超过 FPGA 的 UART_PAYLOAD_BYTES。

GUI 改参数只会改变电脑端；不会自动修改已经烧入 FPGA 的 bitstream。标准版 115200 / 1KB，提速版 2Mbps / 16KB。

示例：发送 0xA5，数据位按 1、0、1、0、0、1、0、1 顺序走

本项目接收器运行在 100MHz：RX 先经过 3 级同步，检测起始位后到位中心确认，再按分频间隔采样 8 位。2Mbps 恰好每位 50 个 UI 时钟；115200 的整数分频为 868。停止位不是高电平就判帧错误，丢弃未完成包并等待恢复。

串口电气接口：这里是板上 3.3V UART，经板载 USB 桥连接电脑。B20 是 FPGA RX，C22 是 FPGA TX。UART 电平接口与 RS-232 的正负电压接口不同，接线依据板级原理图。COM29“拒绝访问”通常发生在 PC 打开端口时：Windows 串口要求独占，一个进程占用时另一个不能打开。见 Microsoft 串口句柄说明。

使用板上的 UART Type-C 接口 P2。P1 是 FT232/JTAG 路线。端口号可能随插拔变化，先在 GUI 中刷新端口列表；已有串口终端或另一个发送 GUI 需要先释放同一个端口。

03 / PIXELS & ADDRESS

图片文件、原始像素与 DDR 地址

PNG/JPEG 文件大小不能直接用来估算传输时间：文件先由电脑解压成像素，再发送固定大小的 RGB565 数据。图片按从上到下逐行、每行从左到右排列，不传文件头，不在 FPGA 上做压缩格式解码。

RGB565 的含义

16bit 像素： RRRRR GGGGGG BBBBB
位位置：      15..11 10..5 4..0
p = (R8 >> 3) << 11
  | (G8 >> 2) << 5
  | (B8 >> 3)

红、蓝各保留 5 位，绿保留 6 位，共 65,536 种编码。显示端用高位复制扩展到 RGB888；这只是把数值展开，不能恢复被丢掉的颜色精度。

小端字节序与位序要分开理解

颜色像素值发送字节
纯红0xF80000 F8
纯绿0x07E0E0 07
纯蓝0x001F1F 00

小端指多字节数值低字节先放；UART 的“最低位先发”则发生在每一个字节内部。两者共同决定线上顺序。

从坐标算地址

stride = 1280 × 2 = 2560 字节 / 行，没有行 padding
frame_bytes = 2560 × 720 = 1,843,200 = 0x001C2000
address(x, y) = frame_base + y × 2560 + x × 2

128bit AXI 数据拍 = 16 字节 = 8 个 RGB565 像素
最低 16bit 对应较早的像素；低字节对应该像素低 8bit。
帧缓冲 0 · 2MiB 地址槽base = 0x00000000

图像有效范围：0x00000000–0x001C1FFF
余下空间不用于本帧像素。

帧缓冲 1 · 2MiB 地址槽base = 0x00200000

图像有效范围：0x00200000–0x003C1FFF
两槽总计预留 4MiB 地址空间。

“帧缓冲 0/1”是两块软件可理解的连续地址区域；哪一块是前台会随换帧变化。代码中的 front_bank / commit_bank 在本页都指这个帧缓冲编号。

04 / DDR3 & AXI

DDR3 基础：为什么有了内存，还需要控制器和 FIFO？

DDR：一个时钟的两个边沿传数据

DDR3 是动态存储器，数据在时钟上升沿和下降沿传输。当前配置物理 CK 为 400MHz，因此是 800MT/s。板上两颗 x16 器件并联，组成 32bit 数据总线。

因此理论 DQ 峰值为 800M × 32 / 8 = 3.2GB/s；实际效率还受到读写切换、刷新、行命中、命令调度等影响。

内部 bank、行与列

DDR3 内部有多个存储 bank，每个包含很多行与列。访问可能需要打开一行、执行读写、关闭或切换行；动态单元还需要周期性刷新，上电后需要初始化和校准。

这些物理存储 bank 与前面的“图像帧缓冲 0/1”不同。线性字节地址如何映射到行、列、bank，由 MIG 配置决定。

MIG 把复杂外设变成总线接口

MIG 是 Xilinx Memory Interface Generator 生成的控制器和 PHY。控制器处理命令、调度和刷新；PHY 处理 DQ/DQS、时钟及采样校准。项目逻辑通过 AXI4 发地址和数据，不直接手写 DDR 引脚时序。

本项目选择在 init_calib_complete 后释放数据通路复位。这个等待条件是本工程的启动策略。

DDR3/MIG 背景资料：AMD UG586 DDR3 SDRAM；校准完成信号见 init_calib_complete。具体速率、位宽、地址槽和启动条件来自本地 MIG 配置与 RTL。

AXI4：读写分成五条独立通道

每条通道都有 VALID 和 READY。同一时钟沿上两者同时为 1，才完成这一拍传输；一旦 VALID 拉高而对方未 READY，地址、数据及相关控制必须保持稳定。AW 地址和 W 数据分别握手，不能假定它们同一周期接收。见 Arm AXI 协议规范。

通道发送方向本项目用途关键点
AW · Write Addressframe_writer → MIG指定后台地址，每次 16 字节AWLEN=0 表示 1 拍；AWSIZE=4 表示 2⁴ 字节/拍。
W · Write Dataframe_writer → MIG128bit 数据；全部字节有效WSTRB=FFFF；WLAST=1；与 AW 独立记录完成状态。
B · Write ResponseMIG → frame_writer确认这一写事务的结果BRESP=OKAY 才继续；整个 DATA 包的 B 响应成功后才回分包 ACK。
AR · Read Addressframe_reader → MIG指定前台读取地址，每次 256 字节ARLEN=15 表示 16 拍；ARSIZE=4；地址递增。
R · Read DataMIG → frame_reader连续接收 16 个 128bit 数据拍逐拍检查 RRESP；RLAST 必须与最后一拍相符。FIFO 满时可背压。

写路径：小流量，重在确认

UART 最快每秒约 20 万原始字节，相比显示带宽很低。写模块把 16 字节装成一拍，等待 AW、W 都握手，再等待 B；一个事务结束才开始下一拍。这样容易明确后台哪些字节已经成功写入。

提速版一包 16KiB，会拆成 1024 个单拍写事务；协议数据包大小与 AXI burst 长度没有直接等号。

读路径：用突发和预取喂显示

读模块每次发出一个 16 拍 / 256B 突发，同方向只保留一个未完成事务。地址 256B 对齐，完整突发不跨 4KB 边界。

FIFO 写端有 1024 个 128bit 字。水位 ≤992 时才启动新突发，留下至少 32 个字的余量；不把平均带宽充足等同于永远不会欠载。

FIFO 是跨域的“蓄水池”，DDR3 是存整张图的“仓库”

DDR 返回数据有间隔，HDMI 有效区却必须每个像素时钟拿出一个像素。异步 FIFO 暂存已经读出的数据，吸收短暂停顿，并把 100MHz、128bit 的输入转换成 74.25MHz、16bit 的输出。

FIFO 容量 = 1024 × 128bit = 16KiB = 8192 像素
若持续按 74.25MHz 消耗：可提供约 110.3µs 的像素
整张图 = 921,600 像素，因此 FIFO 不是整帧缓存。

FIFO 使用 FWFT（First Word Fall Through）：非空时最前面的字已出现在输出端，读使能表示消费它。清 FIFO 或复位时，两个时钟域各自的 busy 未结束前不能恢复读写。接口细节见 AMD XPM_FIFO_ASYNC 文档。

05 / WORK FLOW

一次完整传图，按什么顺序发生？

上电：建立时钟与 DDR3 工作条件

50MHz 晶振经时钟 IP 产生 200MHz，MIG 建立 DDR 工作时钟和 100MHz UI 时钟。视频 MMCM 从 UI 时钟生成 74.25 / 371.25MHz。相关锁定、复位和 DDR 校准满足后，各域同步释放复位。

尚无已发布图片时，front_valid=0，显示有效区输出黑色；此时不会把“没有图片”计成 FIFO 欠载。

GUI 选图：冻结本次发送参数

用户在 images/ 选择自己的图片，确认串口、波特率和分包大小。默认要求 1280×720；显式启用 resize 时由 PC 保持比例缩放并补黑边。GUI 主线程负责界面，后台线程负责转换和串口 I/O。

发送开始才打开串口；完成、停止或异常后关闭。后台经事件队列向界面报告进度，避免等待 ACK 时冻结窗口。

PC 解码：生成唯一的像素字节流

Pillow 解码、处理 EXIF 方向并转换 RGB，再按 RGB565 小端打包成 1,843,200 字节。可选 NumPy 加速与原方法逐字节一致。PC 在这串原始字节上计算整帧 CRC32，并产生本次帧编号。

ABORT → BEGIN：开启后台接收会话

PC 先发 ABORT 清掉可能残留的接收会话，等待应答；再发 BEGIN，携带整帧预期 CRC。写模块选 writer_bank = ~front_bank，清空已确认偏移和帧 CRC 状态。已显示的前台图片保持不变。

DATA：UART 把一包完整送到单包缓存

PC 将原始像素分包，给每包写入命令、序号、帧号、字节偏移等字段，附包 CRC32，进行 7E/7D 转义。FPGA 先收字节、还原转义，在结束分隔符处校验包 CRC。校验通过后才置 packet_valid。

提速版是 112 个 16384B 满包 + 1 个 8192B 尾包，共 113 个 DATA。每包都等待应答，接收器只缓存一个待处理包。

后台写入：16 字节组一拍，每拍等写响应

写模块检查尺寸、格式、包长、帧号和偏移。逐字节读包缓存，更新整帧 CRC；每 16 字节装成一个 128bit 字，向后台地址发 AW 和 W。二者都接收后等待 B，成功才继续下一拍。

接收结束不等于已经写入 DDR；AW/W 接收也不等于事务结果成功。数据路径以 B 响应作为写事务完成依据。

分包 ACK：告诉 PC 可继续的偏移

整个 DATA 包的写响应全部成功后，写模块增加 next_offset；应答模块生成带已确认偏移的 ACK，通过 UART TX 返回。PC 检查命令、序号、帧号、应答 CRC、状态和偏移，才发下一包。

ACK 丢失时 PC 重发相同包。FPGA 识别上一次成功请求的命令、序号、帧号和包 CRC，不重复写入或重复发布。

END：把完整后台帧变成待发布帧

全部像素得到确认后，PC 发 END。FPGA 要求 next_offset=FRAME_BYTES 且整帧 CRC 与 BEGIN 一致。通过后保持 commit_valid / commit_bank / commit_frame，等待读帧模块接受；此时不会立刻回成功 END ACK。

帧首安全窗口：排空旧读事务，交换前台

每次视频扫描回到帧首，像素域发刷新 toggle 和安全窗口。UI 域看到请求后停止新增旧帧读取；已经拉高的 AR 必须完成握手，已经发出的读事务必须排空。回到空闲状态且窗口仍开放时，读模块接受待发布帧并更新前台。

如果 DDR 背压拖到窗口结束，延迟到下一次安全窗口。保持前台不变，不在有效像素区强行换图。

清 FIFO → 重新预取 → 连续输出

换前台时给写模块 commit_ack，它据此回成功 END ACK。同时读模块拉高 FIFO 复位 16 个 UI 周期，再等 XPM 复位 busy 结束，更新 refresh_ack，从新前台偏移 0 预取。

这两个应答的时刻不同：commit_ack 确认前台所有权已交换；refresh_ack 确认这一轮 FIFO 刷新握手完成。END ACK 不是光学测量，也不代表收到 ACK 时屏幕所有行已扫描完。

HDMI 显示：一个像素时钟输出一个像素

有效区逐个消费 FIFO 的 16bit 像素，扩展 RGB888，并与 HS、VS、DE 一起寄存。TMDS 将三种颜色分别编码为 10bit 符号，再经串化器、差分输出到 HDMI1。消隐时发送控制符，不消费图像像素。

下一轮刷新：有新图换图，没有新图重读原图

显示读地址和 FIFO 每轮重新对齐。没有新的完整后台帧时，前台编号不变，再次从偏移 0 读同一张图。下一次上传写另一个地址槽；因而屏幕可以持续刷新，上传尚未完成的半帧不会曝光。

06 / OWNERSHIP & PUBLISH

双缓冲与换帧：如何避免撕裂和混帧？

单缓冲若边读边改，屏幕上部可能属于旧图、下部属于新图。这里用两个独立地址槽：前台供显示读取，后台供接收写入。写模块不会修改当前前台；后台也不会因为“收到一部分”就被显示。

交互演示：从图片 A 换到图片 B

帧缓冲 0 · 0x00000000

帧缓冲 1 · 0x00200000

流程演示说明所有权变化，不是硬件时序仿真。假设 A 在缓冲 0；初次上电没有 A 时，第一张完整图会先写入缓冲 1。

发布的三个门槛

① 数据完整

全部 DATA 按偏移连续接受，字节数达到一帧；每个写事务的 B 响应成功；整帧 CRC 匹配。

② 读事务安全

旧 AR/R 事务已经排空，读模块回到 RUN；不能留下以后才返回、却已经被重新写入的旧帧数据。

③ 显示边界安全

当前存在刷新请求，且跨域后的帧首窗口仍开放。满足条件后才交换角色、清 FIFO。

换帧过程与应答顺序

END 校验通过→commit_valid 保持→帧首 request→排空 AR / R→窗口内交换前台→commit_ack / END ACK→FIFO reset / busy→refresh_ack→新帧预取
信号 / 事件产生与接收实际含义
commit_validframe_writer → frame_reader，均在 UI 域后台帧完整，请发布。缓冲编号、帧号持续保持到接受。
refresh_requestvideo → reader，像素域到 UI 域toggle 变化表示新一轮显示刷新请求；与 ACK 不同表示未完成。
refresh_windowvideo → reader，像素域到 UI 域允许进行 FIFO 重置与角色交换的帧首消隐窗口；提前一整行关闭。
commit_ackreader → writer，UI 域内前台角色已经交换；写模块结束会话，增加 accepted_frames 并发 END ACK。
refresh_ackreader → video，UI 域到像素域FIFO 重置与 busy 等待完成。像素域还需检查 front_valid、FIFO busy 和 empty。
为什么先排空再交换？交换后旧前台会成为下一次上传的后台。如果仍有旧读事务挂着，下一次写入可能与旧事务冲突；排空旧事务也确保 FIFO 不混入上一轮尾部像素。只是改变地址指针不能代替这些步骤。

每个显示帧都执行刷新握手，包括重复显示同一张图片。若换帧窗口错过，读模块等待下一次窗口；视频域如果进入有效区还拿不到对齐后的像素，本帧标记欠载并用洋红提示，避免把错位的数据继续当成正常图片。

07 / FRAME PROTOCOL

串口帧协议：让原始字节可定位、可校验、可重传

UART 只保证按位发送，不知道哪几个字节属于一张图。项目在 UART 字节上加了一层帧协议：分隔符找包边界，长度找 payload，偏移找图片位置，序号与 CRC 支持错误检测和重传。

线上包： 7E | 转义后的 [20B 包头 + payload + 4B 包 CRC32] | 7E
转义规则：原字节 7E → 7D 5E；原字节 7D → 7D 5D
包 CRC：覆盖未转义的包头 + payload，不包含分隔符和 CRC 自身
整帧 CRC：只覆盖全部 RGB565 原始像素；BEGIN 携带该预期值
CRC32 与 Python zlib.crc32 一致；CRC 数值以小端发送。
展开 20 字节包头字段（偏移均指未转义后的包）
字节偏移字段长度约定
0version1B固定 1。
1command1BBEGIN=1，DATA=2，END=3，ABORT=4，QUERY=5。
2–3sequence2B16bit 请求序号；重传复用同一值；成功请求后递增。
4–7frame4B32bit 帧编号，与本次会话保持一致。
8–11offset4B原始图像字节偏移；ACK 中表示下一可接收位置。
12–13length2Bpayload 字节数；不含包头与 CRC。
14–15 / 16–17width / height各 2B固定 1280 / 720。
18 / 19format / reserved各 1Bformat=1：RGB565-LE；reserved=0。

多字节字段全部小端。PC 的结构定义是 <BBHIIHHHBB。未转义包最大大小是 payload 上限 + 24 字节。

命令payload 与 offset成功应答的含义
ABORTPC 发送空 payload；offset=0清接收会话，偏移归零；保持已发布前台不变。
BEGIN4B 整帧预期 CRC；offset=0已选定后台槽，开始一个新帧会话。
DATA正数且为 16B 倍数；offset 必须等于 next_offset本包所有 AXI 写响应成功；返回新的已确认偏移。
END空 payload；offset=1,843,200完整帧已被读模块接受为前台；不是刚收到包就应答。
QUERY空 payload报告当前已确认偏移，不改变会话；正常 GUI 传图不需要它。

ACK / NACK 如何返回？

应答仍使用同样的包头、转义和包 CRC。命令为请求命令 OR 0x80；payload 是 1 字节状态，0 为成功，其余为错误。正常应答回带请求序号和帧号；无法关联具体请求的包错误/超时使用通用命令 0x80、序号 0xFFFF。

停等与重试

电脑只保留一个在途请求。默认一次请求最多发送 4 次，重试使用完全相同的编码包。等应答的预算包含请求线速时间及额外 2 秒；状态 2、4、8 可以进入重试，其他错误通常终止本次发送。

FPGA 保存最近一次成功命令的去重信息；相同成功包再来时直接回成功，避免 DATA 重复写、END 重复发布。

两种 CRC 分别挡住什么错误？

包 CRC 在任何写入前检查，挡住这一包字节损坏；整帧 CRC 在 END 检查，确认完整像素流与 PC 一致。偏移和帧号检查则挡住漏包、乱序及混用其他会话。

这些检查保护发布结果；DDR 部分写入失败后可残留后台数据，但后台不会因此被切成前台。

标准 payload 1024B：1800 个 DATA；提速 payload 16384B：113 个 DATA。GUI 进度依据成功 DATA ACK，不依据已写进操作系统缓冲区的字节数；100% 后仍要等待 END 发布应答。

08 / 720p & TMDS

HDMI 基础：720 行图像之外，还需要什么？

显示器需要稳定的扫描节奏。每行包含有效像素和水平消隐，每帧包含有效行和垂直消隐。HS/VS 告诉接收端行、帧同步位置；DE=1 表示当前 RGB 是有效画面。消隐也占用像素时钟，因此时钟频率不能只按 1280×720×60 计算。

方向有效区前肩 Front同步 Sync后肩 Back总计
水平 · 像素时钟数1280110402201650
垂直 · 行数7205520750
像素时钟 = 1650 × 750 × 60 = 74,250,000Hz = 74.25MHz
一行时长 ≈ 22.22µs；一帧时长 ≈ 16.67ms
HS / VS：正极性；有效画面每帧恰好消费 1280 × 720 个像素。

本代码的计数原点在同步区起点

扫描顺序按 Sync → Back → Active → Front 循环。H 有效区从计数 260 开始；V 有效区从行 25 开始。它与“Active → Front → Sync → Back”的画法只是原点不同。

刷新 request 在 h=0、v=0 产生；refresh_window 按 v < 24 注册，在有效区开始前留出一整行关闭裕量。它是帧首窗口，不是整个消隐期都允许换图。

RGB 与控制信号要对齐

FWFT FIFO 给出当前待消费像素。视频模块在同一像素时钟寄存 RGB、HS、VS、DE，以免颜色晚一拍而 DE 提前一拍。只有有效区、刷新就绪、FIFO 非空且本帧未欠载时才消费像素。

无前台图片输出黑色；已有前台但像素未就绪时，该帧余下有效区显示 FF00FF 洋红，下一帧重新同步。

从 RGB888 到 HDMI 差分线

每像素 R/G/B 各 8bit→3 个 TMDS 编码器，各出 10bit→OSERDESE2 主从 10:1→OBUFDS / TMDS_33→3 对数据 + 1 对时钟

TMDS 编码控制转换次数和直流偏置；消隐时发送控制符，蓝色通道携带 HS/VS。每像素每数据通道要发 10bit：串化器用 371.25MHz 时钟的双边沿输出，得到 742.5Mbps 每通道。时钟通道输出对应 74.25MHz 的差分像素时钟。

当前输出范围：固定 720p60 视频经 HDMI 接口输出，属于 DVI 兼容的 TMDS 视频通路。没有音频、HDCP、EDID/DDC 读取或 HPD 配置流程。显示器对当前固定模式的实际兼容性仍需要上板确认。

跨域内容处理方式为什么这样做
外部 UART RX → UI3 级输入同步，再进行位采样异步输入可能接近采样边沿；同步链降低亚稳态传播风险。
UI 像素 → pixelXPM 异步 FIFO；128bit 写 / 16bit 读多位像素必须保持完整、顺序一致，不能逐位同步后拼起来。
pixel request → UI / UI ACK → pixeltoggle 状态保持；目标域两级同步窄脉冲可能被较慢或不同相位时钟漏掉，保持状态直到应答更可靠。
pixel refresh_window → UI注册窗口后两级同步；提前一行关闭读模块在目标域判断安全期，并为跨域延迟留出边界裕量。
UI front_valid → pixel两级同步；配合刷新 ACK 使用告诉视频模块是否有完整图片；不跨域采样整个地址或帧号。
复位、锁定、校准各时钟域 reset_sync，异步置位、同步释放允许及时停止，但恢复运行必须对齐各域时钟边沿。

front_bank、commit_bank 和帧号保持在 UI 域，由 UI 读写模块协作；像素域只接收 FIFO 像素及少量同步后的控制状态。FIFO 使用两级内部 CDC，同步指针与 full/empty 信息。

复位是流程的一部分：DDR 校准、视频锁定丢失或系统复位时，数据通路重新进入等待状态。正常帧刷新则只重置显示 FIFO 和读偏移。XPM 的 busy 握手必须完成才能读写；本工程利用 XPM 写端 busy 的内部复位握手，未重复把同一个读端 busy 再跨回 UI 形成重汇聚。
10 / MODULE RESPONSIBILITIES

主要模块分别干了什么？

下面按数据流分工列出源码入口。阅读代码时，建议先看 top 的连接，再顺着接收、写帧、读帧、显示四段理解状态机。

send_image_gui.py · 人机界面

PC / Tk 主线程 + worker / 事件队列

枚举串口、选择图片和参数、显示预览/进度/日志，提供标准与提速预设。发送线程持有本次参数快照；界面不直接阻塞等待串口。停止时取消等待读写并释放端口。

边界：界面进度按 ACK 更新；已经发布的图不会被“停止”撤回。

send_image.py · PC 端协议引擎

图片 → RGB565-LE → Packet → Serial → ACK

负责选图/解码/缩放、RGB565 打包、整帧和包 CRC、SLIP 转义、序号、停等、重传和应答匹配。GUI 与命令行共用这一份实现。

边界：DATA ACK 偏移必须与预期一致；图片尺寸/格式由 PC 校验后发送。

uart_rx_8n1 / uart_tx_8n1 · 位与字节

ui_clk 100MHz / RX 输入同步 / TX valid-ready

RX 检测起始位、居中采样、检查停止位，输出 data/valid/framing_error。TX 在可接受时锁存字节，输出起始、8 位数据、停止位，空闲保持高。

边界：只知道字节，不知道图片、分包或 DDR。波特率由综合参数决定。

packet_rx · 单包接收与校验

ui_clk / 字节输入 → packet_valid + 缓存读口

识别 7E 边界、还原 7D 转义、统计长度、积累 CRC。合法完整包保留在缓存，供 frame_writer 一字节一字节读取，consume 后释放。

边界：缓存满、CRC 错、悬空转义、帧错误和字节间超时要恢复；valid 待消费期间不能接受第二个包。

frame_writer · 接收会话与后台写帧

ui_clk / 包缓存 → AXI AW/W/B → commit

解析 20B 头，检查尺寸/格式/长度/帧号/偏移，选择后台；组 128bit 数据并逐拍等待写响应，更新帧 CRC 和已确认偏移。保存最近成功请求以处理重复包。

状态主线：IDLE → HEADER → CHECK → LOAD → WRITE → RESPONSE；END 进入 PUBLISH 等 commit_ack，最后 REPLY。

边界：没有完整字节数、正确帧 CRC 和成功 B 响应，就不发布。

packet_reply · 应答封装

ui_clk / reply valid-ready → UART TX 字节流

锁存命令、状态、序号、帧号、已确认偏移，生成 20B 头 + 1B 状态 + CRC；补分隔符、转义并按 UART TX 的 ready 节奏逐字节发送。

边界：转义后两个线上字节仍只对应一个原始 CRC 字节；应答不能因 TX 背压被截断。

MIG · uart_mig 配置

200MHz sys/ref / DDR CK 400MHz / UI 100MHz

由 Vivado 生成的 DDR3 控制器和 PHY，连接板上 DQ、DQS、地址和控制引脚。向业务逻辑提供 30bit 字节地址、128bit AXI 数据、响应和校准状态。

边界：FPGA 工具/IP、器件、电压、引脚和内存型号必须匹配；业务逻辑不把它当作通用可移植 RTL。

frame_reader · 前台读出与发布仲裁

ui_clk / AXI AR/R → FIFO 写端 / front ownership

按 FIFO 水位预取 256B 突发，检查 RRESP、RLAST 和拍数；收到刷新请求后排空旧事务，在安全窗口内接受新前台，重置 FIFO、读偏移并完成刷新握手。

状态：RUN → ADDRESS → DATA → RUN；刷新时 RUN → RESET_FIFO → WAIT_FIFO → RUN。

边界：AR 已拉高就必须等握手，不能因窗口关闭撤销；未排空不交换。

XPM FIFO · top 中实例

UI 写 128bit / pixel 读 16bit / 16KiB / FWFT

承担跨时钟域、位宽转换与短时数据缓冲。内部同步读写指针；输出 full/empty、写端水位和两端 reset busy。

边界：它不负责图像帧号与所有权，换帧时必须显式重置；读空、写满和 busy 期间不能操作。

video_720p · 扫描时序与取像素

pixel_clk 74.25MHz / FIFO → RGB + HS + VS + DE

维护水平/垂直计数，生成刷新 request/窗口，按有效区消费像素并扩展颜色。同步前台有效状态和刷新 ACK；RGB 与控制一起寄存。

边界：每帧一次欠载计数；本帧一旦欠载，余下像素用洋红，避免重新消费后错行。

tmds_output · 视频物理输出

pixel 74.25MHz + serial 371.25MHz / 差分输出

连接三个 hdmi_encoder 和四个 hdmi_serializer10to1，包括时钟通道。编码有效像素/消隐控制符，10:1 串化后经 OBUFDS 输出。

边界：复用了厂商参考代码，保留原版权；需要 Xilinx 原语和仿真库。

video_clocks / reset_sync

视频时钟生成 / 各域复位同步释放

video_clocks 用 MMCM 从 UI 派生两路视频时钟和 locked。reset_sync 在目的时钟域安全释放复位；像素域分别处理独立复位来源再组合。

边界：调整分辨率必须同时核对时序、像素时钟、5×串化时钟和约束，不能只改有效宽高。

uart_hdmi_top · 系统装配

顶层引脚 / 参数 / 时钟复位 / AXI 与 FIFO 连接

实例化所有业务模块及 MIG、Clock Wizard、XPM；设置 UART 参数、包缓存长度、会话超时和 AXI 固定属性。保留内部统计信号，控制显示输出使能。

边界：当前没有 OSD FPS、神经网络、摄像头或 RISC-V；内部计数也没有被全部导出到 GUI。

create_project.py / estimate_transfer.py

构建工具 / 性能预算工具，不参与板上数据流

错误发生时，系统如何保住当前画面？

情况逻辑行为恢复 / 用户可见结果
COM 端口无法打开PC 打开端口即失败，还未发图片。检查当前端口与占用程序；关闭占用串口的终端或另一 GUI 后重试。改 FPGA 波特率不能解除端口占用。

包 CRC 错 / 转义不完整 / 超长包packet_rx 不置合法 packet_valid，丢弃该包，不写 DDR。错误应答或超时后，PC 重发相同包；分隔符重新建立边界。
中途断线，半个包残留顶层配置 1s 字节间空闲超时，清未完成包。不是“整个包必须 1s 内传完”；收到连续字节会刷新计时。
BEGIN 后长期没有新请求写引擎处于 IDLE、会话仍活动且无 RX 活动 5s，清会话。前台不变；下一次发送从 ABORT / BEGIN 重新开始。不是“整帧传输最多 5s”。
尺寸、格式、长度、偏移不正确状态 1 或 3 拒绝请求，不能把字节写到错误位置。终止本次发送，检查软硬件配置，重新开启会话。
成功 ACK 丢失同一成功请求重发时用缓存去重，不重复写/发布。返回同一成功结果；PC 检查偏移后继续。
AXI 写 BRESP 错 / 整帧 CRC 错状态 5 / 6；接收会话终止，后台不发布。当前前台图片保留；重新传图并排查 DDR/协议问题。
读 RRESP 错 / RLAST 不符合拍数异常拍不进入 FIFO；标记 frame_fault，停止继续正常预取，排空当前响应。本轮可能出现洋红欠载标记；下一轮显示刷新重新对齐，并记录 read_errors。
DDR 背压拖过换帧窗口保留已经拉高的 AR，排空响应；窗口结束后不强行换帧。新图延后发布，直到下一次安全窗口。
FIFO 不足 / 刷新尚未完成已有前台时有效区第一次缺像素，本帧锁定 frame_bad。本帧剩余有效区洋红；下一帧清标记并重新同步。没有前台时黑屏。
AXI 从设备永久不回应当前没有强行取消在途 AXI 事务的机制。PC 超时不等于总线恢复；若控制器永久挂住或永远不返回 RLAST，需要系统复位及进一步定位。
应答状态码对照

0 OK；1 头部/尺寸/长度错误；2 包 CRC/帧错误；3 帧号/偏移顺序错误；4 接收会话忙；5 DDR AXI 错误；6 整帧 CRC 不匹配；7 会话超时；8 DDR 未校准。实际未校准时顶层通常仍保持协议通路复位，因此也可能表现为没有应答，而不是一定返回 8。

12 / PERFORMANCE

为什么原来约 160 秒？2Mbps 能否进 10 秒？

纯像素最低线速时间 = 图像字节数 × 10 / 波特率
115200：1,843,200 × 10 / 115200 = 160.000s
2Mbps： 1,843,200 × 10 / 2,000,000 = 9.216s

160 秒与 RGB565 原始像素在 115200 的纯线速下限相符。把 1KB 改成 16KB 主要减少停等次数和固定开销；真正大幅缩短像素发送时间的是提高双方波特率。当前仍传完整 720p RGB565，没有降低输入分辨率。

921600 / 1KB180020.000s数学对照，不代表有对应已验证 bitstream。
1500000 / 16KB11312.288s数学对照，仍不能满足纯线速 10s。
2000000 / 16KB1139.216s独立提速工程/bitstream 已生成，实板待测。

线速下限计算器 · 当前固定 720p RGB565

假设每个成功请求都有 ACK，不重传。固定协议下限还计入 ABORT、BEGIN、END、包头、CRC、分隔符和成功 ACK；不计依赖具体内容的 7D/7E 转义，以及 USB、DDR、软件、换帧等待。这里的数值不修改 GUI、FPGA 或串口。

10 秒目标仍要实测：按目前 34 张图、指定帧号 0、2Mbps / 16KB 统计，包含实际转义、包头与成功 ACK 的线速预算为 9.2475–9.7876s。余量有限，USB 桥持续发送能力、包间等待、DDR、图像解码、换帧或重试还会增加总时间。不能把这个预算写成实际 10s 已通过。

显示通路需要的 DDR 带宽

110.592 MB/s平均像素读取：1280 × 720 × 2 × 60

有效像素区内的瞬时消费速度为 74.25M × 2 = 148.5MB/s；消隐期可用于预取。

峰值不能代替稳定性验证

DDR3 DQ 理论 3.2GB/s 远高于平均需求，但本项目 UI、单在途读突发、控制开销及暂停会限制实际通路。需结合读响应间隔、FIFO 水位及 underflow_frames 判断持续供像素能力。

GUI 最终耗时包含解码、打开端口、命令、像素和应答；成功 END ACK 表示发布确认。HDMI 60Hz 刷新、串口新图更新率和未来神经网络推理 FPS 必须分别报告，重复扫描同一图片不能算作新处理帧。
